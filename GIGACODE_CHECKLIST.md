# Проверка GigaCode: исполняемые файлы для Zsh

Вместо копирования функций в терминал подготовлены два исполняемых файла:

- [scripts/check-gigacode.zsh](scripts/check-gigacode.zsh) — основные проверки.
- [scripts/check-gigacode-acp.zsh](scripts/check-gigacode-acp.zsh) — проверка инициализации ACP.

Скопируй оба файла в одну папку на машине с настроенным GigaCode. Второй использует
первый, поэтому их нужно держать рядом. Скрипты можно запускать из любого каталога.
Они сами создают новый временный рабочий каталог и отдельный архив результатов.
Установка зависимостей Teamytime не требуется: используются Zsh и стандартные утилиты
macOS/Linux (`mktemp`, `mkdir`, `tar`, `uuidgen`; для ACP — `mkfifo`).

## Запуск из репозитория

```zsh
./scripts/check-gigacode.zsh
./scripts/check-gigacode-acp.zsh
```

Каждый скрипт напечатает путь `Archive: .../teamytime-probe-results.tar.gz`.
Пришли оба архива; они находятся в разных каталогах, хотя называются одинаково.
В первом запуске выполняются короткие задания моделей, во втором отправляется
только запрос инициализации ACP.

Если при переносе потеряется право на исполнение, можно запустить файлы напрямую через Zsh:

```zsh
zsh -f ./scripts/check-gigacode.zsh
zsh -f ./scripts/check-gigacode-acp.zsh
```

Если скопировал файлы в отдельную папку без каталога `scripts`, из этой папки команды будут:

```zsh
zsh -f ./check-gigacode.zsh
zsh -f ./check-gigacode-acp.zsh
```

## Выбор моделей и исполняемого файла

По умолчанию используется модель из настроек GigaCode. Это проверяет разные сессии,
но не работу разных моделей. Для проверки двух моделей укажи их реальные идентификаторы:

```zsh
./scripts/check-gigacode.zsh --model-a 'ID_ПЕРВОЙ_МОДЕЛИ' --model-b 'ID_ВТОРОЙ_МОДЕЛИ'
```

Идентификаторы можно посмотреть в интерактивном GigaCode через `/model`.
Если GigaCode доступен только через alias или функцию оболочки, передай путь
к установленному исполняемому файлу:

```zsh
./scripts/check-gigacode.zsh --gigacode /полный/путь/к/gigacode
```

Все параметры показаны в справке, которая не запускает GigaCode:

```zsh
./scripts/check-gigacode.zsh --help
```

## Что выполняет основной скрипт

| Проверка | Что сохраняется и что будем проверять |
| --- | --- |
| Версия, текущий help и справка MCP | Доступные параметры установленной версии |
| Создание A и B | Две разные сессии, модели и инструкции ролей |
| Продолжение A после создания B | A должен вспомнить `ORBIT_7319` без повторной передачи этого слова |
| Одновременное продолжение A и B | A должен помнить `ORBIT_7319`, B — `CEDAR_4826` |
| Частичные сообщения | Структура частичных событий и итогового ответа |
| Инструменты в режиме Gigaflex | Вызов `run_shell_command` и создание тестового файла с `TEAMYTIME_TOOL_OK` |

Обе сессии работают в одном новом каталоге. Их ID генерируются отдельно через `uuidgen`.
Повторные сообщения направляются через `--resume <ID>`. Флаг `--continue` не используется.
Запись истории включается через `--chat-recording`.

В первом продолжении A инструкции роли повторно не передаются: наличие `ROLE_A:` в
ответе поможет оценить их сохранение. В параллельном запуске инструкции передаются явно.
Скрипт не запускает два процесса для одной сессии одновременно.

Создание с заданным UUID и сочетания параметров проверяются экспериментально. Если
создание сессии завершилось с ошибкой или по таймауту, зависимые проверки пропускаются.
Скрипт сохраняет причину пропуска. Ошибка назначения ID не доказывает отсутствие
продолжения сессий, созданных самим CLI.

В проверке инструментов сохранён исторический `-p`, чтобы сопоставить поведение с Gigaflex.
Если текущая версия уже удалила этот параметр, ошибка попадёт в результаты.

## Что выполняет ACP-скрипт

Он получает версию и текущий help, запускает `gigacode --acp`, автоматически передаёт
через stdin следующий запрос и сохраняет ответ:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":1,"clientCapabilities":{},"clientInfo":{"name":"teamytime-probe","version":"0.1.0"}}}
```

Скрипт удерживает stdin открытым во время ожидания. После появления сообщения с ID 1
либо по истечении 30 секунд он завершает процесс и сохраняет журналы. Наблюдение ID 1
не считается доказательством успешной инициализации: в журнале может быть JSON-RPC-ошибка.
Проверим содержимое ответа, `protocolVersion`, `agentInfo`, `agentCapabilities` и `loadSession`.

Ненулевой код выхода после остановки самим ACP-скриптом ожидаем. Файл
`08-acp.stopped-by-probe.txt` отличает такую остановку от самостоятельного завершения CLI.

Запрос основан на [инициализации ACP v1](https://agentclientprotocol.com/protocol/v1/initialization)
и [транспорте stdio](https://agentclientprotocol.com/protocol/v1/transports).
Он проверяет именно ACP; формат обычного `--input-format stream-json` — отдельный протокол.

## Таймауты, прерывание и результаты

На один вызов модели по умолчанию отводится 180 секунд. Изменить лимит можно так:

```zsh
./scripts/check-gigacode.zsh --timeout 300
```

Метаданные и ACP ожидаются не более 30 секунд. При таймауте скрипт останавливает
запущенный процесс CLI и сохраняет отдельную отметку. Ctrl+C останавливает проверку
и запускает сохранение уже собранных результатов.

Для каждой команды сохраняются аргументы, stdout, stderr и код выхода. Прогресс виден
в терминале, а полные ответы читаются из файлов. Время появления отдельных частичных
событий пока не измеряется.

Коды выхода основного скрипта:

- `0` — запрошенные процессы завершились ожидаемым образом; содержимое ответов ещё нужно проверить.
- `1` — были ошибки процессов, таймауты или пропущенные проверки.
- `2` — ошибка параметров либо подготовки окружения.
- `130` — пользователь прервал работу через Ctrl+C.

Код 0 не означает, что модель действительно сохранила контекст, выбрала нужную роль
или выполнила задачу: для этого нужны ответы и события инструментов из журнала.

В архив попадает только каталог `results` текущего запуска. Полное хранилище сессий,
конфигурацию авторизации и системные настройки отдельно собирать не нужно.
Многоходовый потоковый ввод, доставка сообщения во время активного хода и полноценное
восстановление после сбоя остаются следующими проверками после разбора этих результатов.
