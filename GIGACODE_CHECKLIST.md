# Что запустить на машине с GigaCode

Выполняй блоки по порядку в одном окне Bash или Zsh на macOS/Linux.
Понадобятся настроенный GigaCode, `uuidgen` и `tar`. Устанавливать зависимости проекта не нужно.
Проверки используют короткие синтетические задания и создают несколько сессий.

Команды основаны на предоставленном историческом help. Сначала сохраняем текущий help:
если нужного параметра больше нет или он изменился, сохрани ошибку и пропусти зависимые
проверки. Ошибка отдельной проверки не мешает собрать остальные результаты.

## 0. Подготовить отдельный каталог и сохранение результатов

```bash
export TT_ROOT="$(mktemp -d "${TMPDIR:-/tmp}/teamytime-probe.XXXXXX")"
export TT_RESULTS="$TT_ROOT/results"
mkdir -p "$TT_RESULTS" "$TT_ROOT/workspace"
cd "$TT_ROOT/workspace"

tt_run() {
  local tt_name="$1"
  shift
  printf 'Running %s\n' "$tt_name"
  "$@" </dev/null >"$TT_RESULTS/$tt_name.stdout.log" 2>"$TT_RESULTS/$tt_name.stderr.log"
  local tt_exit=$?
  printf '%s\n' "$tt_exit" >"$TT_RESULTS/$tt_name.exit.txt"
  printf '%s: exit=%s\n' "$tt_name" "$tt_exit"
  cat "$TT_RESULTS/$tt_name.stdout.log"
  cat "$TT_RESULTS/$tt_name.stderr.log"
  return 0
}

tt_agent() {
  local tt_name="$1"
  local tt_model="$2"
  shift 2
  local -a tt_model_args
  tt_model_args=()
  if [ -n "$tt_model" ]; then
    tt_model_args=(--model "$tt_model")
  fi
  tt_run "$tt_name" gigacode "${tt_model_args[@]}" \
    --chat-recording \
    --approval-mode plan \
    --output-format stream-json \
    --max-session-turns 8 \
    "$@"
}

printf 'Results directory: %s\n' "$TT_ROOT"
```

`tt_run` сохраняет stdout, stderr и настоящий код завершения GigaCode раздельно.
Сама функция возвращает управление даже после ошибки; результат команды смотри в
`*.exit.txt`. Вывод обычных проверок появится после завершения процесса.
Если команда зависла, нажми Ctrl+C и переходи дальше. Уже записанные журналы сохранятся;
отсутствие файла с кодом завершения после прерывания допустимо.

Каталог `results` находится рядом с рабочим каталогом, а не внутри него.

## 1. Сохранить версию и актуальную справку

```bash
command -v gigacode >"$TT_RESULTS/01-path.txt"
tt_run 01-version gigacode --version
tt_run 01-help gigacode --help
tt_run 01-mcp-help gigacode mcp --help
```

Нужно увидеть доступность `--resume`, `--session-id`, `--chat-recording`, `--model`,
`--append-system-prompt`, `--input-format`, `--output-format`,
`--include-partial-messages`, `--max-session-turns` и `--acp`.
Версия и help сами по себе не подтверждают совместимость этих параметров между собой.

## 2. Указать модели и создать разные ID участников

Если идентификаторы моделей неизвестны, открой `gigacode`, выполни `/model`, запиши
доступные идентификаторы и выйди через `/quit`. Не меняй настройки специально для проверки.
Названия в интерфейсе могут отличаться от идентификаторов, которые принимает `--model`.

В строках ниже можно указать два реальных идентификатора. Пустая строка означает модель
из настроек CLI: в таком случае флаг `--model` вообще не передаётся. Два пустых значения
позволяют проверить сессии, но не доказывают работу с разными моделями.

```bash
export TT_MODEL_A=''
export TT_MODEL_B=''
export TT_SESSION_A="$(uuidgen | tr '[:upper:]' '[:lower:]')"
export TT_SESSION_B="$(uuidgen | tr '[:upper:]' '[:lower:]')"

printf 'MODEL_A=%s\nMODEL_B=%s\nSESSION_A=%s\nSESSION_B=%s\n' \
  "$TT_MODEL_A" "$TT_MODEL_B" "$TT_SESSION_A" "$TT_SESSION_B" \
  >"$TT_RESULTS/02-participants.txt"
```

UUID используется как кандидат формата ID. Если CLI отвергнет `--session-id`, это важный
результат. Сохрани ошибку; проверки продолжения этих сессий пока пропусти. Неподдержанный
способ назначения ID не доказывает отсутствие продолжения сессий, созданных самим CLI.

## 3. Создать два участника с разными ролями и контекстом

```bash
tt_agent 03-create-a "$TT_MODEL_A" \
  --session-id "$TT_SESSION_A" \
  --append-system-prompt 'Ты координатор тестовой команды. Каждую реплику начинай с ROLE_A:. В этой проверке не используй инструменты, файлы, память вне разговора или поиск.' \
  'Запомни контрольное слово ORBIT_7319 только в контексте этого разговора. Ответь коротко, что запомнил его.'

tt_agent 03-create-b "$TT_MODEL_B" \
  --session-id "$TT_SESSION_B" \
  --append-system-prompt 'Ты рецензент тестовой команды. Каждую реплику начинай с ROLE_B:. В этой проверке не используй инструменты, файлы, память вне разговора или поиск.' \
  'Запомни контрольное слово CEDAR_4826 только в контексте этого разговора. Ответь коротко, что запомнил его.'
```

Ожидается: обе команды завершаются, ответы имеют свои префиксы, в JSON видны
идентификаторы сессий и, если CLI их сообщает, фактические модели. Нужны именно полные
журналы: код 0 без осмысленного ответа ещё не означает успех.

## 4. Продолжить A после создания B, не передавая старый контекст

```bash
tt_agent 04-resume-a "$TT_MODEL_A" \
  --resume "$TT_SESSION_A" \
  'Не используй инструменты или файлы. Назови контрольное слово, которое я сообщил в предыдущем ходе этого разговора. Если не помнишь, напиши НЕ ПОМНЮ.'
```

Ожидаем слово `ORBIT_7319`. В новом промпте его нет. Это проверяет продолжение
конкретной сессии после завершения процесса, когда последней создана другая сессия.
`--continue` здесь намеренно не используется.

Инструкции роли в этом запуске не передаются повторно. Префикс `ROLE_A:` покажет, сохранились
ли они в данном сценарии. Один удачный ответ не является полной гарантией поведения
системного промпта при всех следующих продолжениях.

## 5. Продолжить A и B одновременно в одном рабочем каталоге

```bash
tt_agent 05-parallel-a "$TT_MODEL_A" \
  --resume "$TT_SESSION_A" \
  --append-system-prompt 'Ты координатор. Начни ответ с ROLE_A:. Не используй инструменты или файлы.' \
  'Назови контрольное слово из предыдущих сообщений этого разговора. Если не помнишь, напиши НЕ ПОМНЮ.' &
TT_PID_A=$!

tt_agent 05-parallel-b "$TT_MODEL_B" \
  --resume "$TT_SESSION_B" \
  --append-system-prompt 'Ты рецензент. Начни ответ с ROLE_B:. Не используй инструменты или файлы.' \
  'Назови контрольное слово из предыдущих сообщений этого разговора. Если не помнишь, напиши НЕ ПОМНЮ.' &
TT_PID_B=$!

wait "$TT_PID_A"
wait "$TT_PID_B"
```

Ожидается: A помнит `ORBIT_7319`, B помнит `CEDAR_4826`; обе сессии могут выполняться
одновременно. Вывод в терминале может перемешаться, но файлы результатов раздельные.
Проверка не запускает два процесса для одной сессии. Ограничение API по параллельности
следует отличать от ошибки изоляции сессий.

## 6. Проверить частичные сообщения для живого интерфейса

```bash
tt_agent 06-partials "$TT_MODEL_A" \
  --include-partial-messages \
  'Не используй инструменты или файлы. Напиши 12 пронумерованных коротких предложений о совместной работе команды. Каждое предложение с новой строки.'
```

В `06-partials.stdout.log` проверим наличие частичных событий, итогового ответа и
признака завершения. Эта команда собирает структуру потока; момент появления событий
в реальном времени отдельно не измеряется, поскольку helper показывает журнал после завершения.

## 7. Проверить реальную работу с инструментом в режиме Gigaflex

Этот шаг создаёт один тестовый файл в подготовленном рабочем каталоге.
Используется знакомый по Gigaflex режим `auto-edit` с разрешённым `run_shell_command`.
Модель берётся из текущих настроек CLI.

```bash
tt_run 07-tools gigacode \
  --chat-recording \
  --approval-mode=auto-edit \
  --allowed-tools run_shell_command \
  --output-format stream-json \
  --max-session-turns 8 \
  -p 'Выполни через run_shell_command: pwd; затем создай в текущем каталоге файл teamytime-probe.txt с единственной строкой TEAMYTIME_TOOL_OK и прочитай его через cat. Не выполняй другие действия. В финальном ответе укажи прочитанную строку.'

if [ -f teamytime-probe.txt ]; then
  cat teamytime-probe.txt >"$TT_RESULTS/07-created-file.txt"
fi
```

Ожидается файл с `TEAMYTIME_TOOL_OK`, подтверждающие вызовы инструментов в журнале и
успешное завершение без ожидания интерактивного разрешения.
Здесь `-p` оставлен для сопоставимости с Gigaflex. Если текущий CLI уже удалил этот флаг,
сохрани ошибку; она покажет необходимость изменения адаптера.

## 8. Узнать заявленные возможности ACP

Это отдельная проверка интерфейса управления агентом. Она не отправляет модели задачу
и не проверяет формат обычного `--input-format stream-json`.

Запусти:

```bash
gigacode --acp 2>"$TT_RESULTS/08-acp.stderr.log" | tee "$TT_RESULTS/08-acp.stdout.log"
```

Если процесс остался работать, вставь следующую строку и нажми Enter:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":1,"clientCapabilities":{},"clientInfo":{"name":"teamytime-probe","version":"0.1.0"}}}
```

После ответа с `"id":1` нажми Ctrl+C. Если ответа нет примерно 30 секунд, также нажми
Ctrl+C. Если CLI сразу вернулся в командную строку с ошибкой, JSON вставлять не нужно.
Код завершения `tee` не является кодом завершения GigaCode и здесь не используется.

В ответе интересны `protocolVersion`, `agentInfo`, `agentCapabilities`, в особенности
`loadSession`, и описание способов авторизации. Этот обмен подтверждает только
инициализацию ACP и заявленные возможности, а не успешное продолжение через ACP.

Запрос соответствует [инициализации ACP v1](https://agentclientprotocol.com/protocol/v1/initialization).
Передача одной JSON-RPC-строки на сообщение описана в [транспорте stdio](https://agentclientprotocol.com/protocol/v1/transports).
Поддержку этой версии самим GigaCode покажет результат.

## 9. Собрать результаты и прислать архив

```bash
printf '%s\n' 'Необязательная заметка: замени этот текст, если какие-то шаги были пропущены или прерваны.' \
  >"$TT_RESULTS/09-notes.txt"
tar -czf "$TT_ROOT/teamytime-probe-results.tar.gz" -C "$TT_ROOT" results
printf '\nПришли этот файл: %s\n' "$TT_ROOT/teamytime-probe-results.tar.gz"
```

В архив попадает только каталог результатов этой проверки. Системные настройки,
каталог авторизации GigaCode и полное хранилище сессий отдельно собирать не нужно.
Если архив передать неудобно, пришли сначала версию, актуальный help и журналы шагов 3–5.

## Что решим по результатам

- Можно ли создавать и адресно продолжать независимые сессии участников.
- Как передавать инструкции ролей и проверять фактически используемую модель.
- Работают ли разные участники параллельно при общей авторизации и рабочем каталоге.
- Как устроены частичные ответы и события инструментов.
- Подходит ли режим выполнения Gigaflex для этого окружения.
- Какие возможности объявляет ACP и стоит ли проверить его дальше.

Многоходовый обмен через обычный `--input-format stream-json`, доставка сообщения во время
активного хода, отмена и восстановление после сбоя остаются следующими проверками.
Для потокового ввода исторический help не содержит схемы сообщений. Ошибка при отправке
произвольно выбранного JSON не могла бы доказать отсутствие этой возможности.
